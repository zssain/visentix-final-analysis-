VISENTIX MVP — AUDIT vs "How The App Works" PDF Spec
=====================================================
Date: 2026-06-29
Auditor: Claude Code (automated scan of codebase + database)

This file compares every requirement in the PDF spec against what
actually exists in the codebase and database.

Legend:
  [BUILT]   = Fully implemented and tested
  [PARTIAL] = Implemented but incomplete or has gaps
  [MISSING] = Not implemented
  [STUB]    = Placeholder exists, needs real content

======================================================================
STAGE 1 — THE FRONT DOOR: getting the notice in and reading it
======================================================================

[BUILT] Upload — 3 input shapes (URL, PDF, pasted text)
  File: app/services/intake/extract.py
  Route: POST /assessments/ (app/routers/assessments.py)
  - URL: SSRF-safe fetch with DNS resolution check
  - PDF: PyMuPDF extraction (no shell-outs)
  - Text: length-bounded (500K chars)
  Tests: tests/test_intake.py (31 tests)

[BUILT] Decompose — sections -> clauses + content hash
  File: app/services/intake/decompose.py
  - Splits on headings / double-newlines
  - SHA-256 content hash for change detection
  - Matches existing corpus schema (notice -> section -> clause)

[PARTIAL] Classify — AI labels each clause into 8 domains
  File: app/services/intake/decompose.py (keyword-based classify_clause)
  File: app/services/llm.py (LLM-based classify via Qwen)
  WHAT'S BUILT:
    - Keyword-based classification into 8 domains (works offline)
    - LLM client with classify() method (local Ollama + hosted)
    - JSON-constrained output mode for classification
  WHAT'S MISSING:
    - The live POST /assessments endpoint uses keyword classification,
      NOT the LLM. The llm.classify() exists but is not wired into
      the intake pipeline. The PDF says live notices should use hosted
      Qwen for classification.
    - trafilatura is mentioned in the PDF for text extraction but we
      use PyMuPDF + manual splitting instead. Functional equivalent
      but different library.
  GAP SEVERITY: Medium — keyword classification works but the 65%
    "other/unclassified" gap in the corpus won't be resolved until
    LLM classification is wired in for reclassification.

STAGE 2 — THE BRAIN: turning text into intelligence
======================================================================

[BUILT] Company Profile — 7 scores (IC, RSS, PGMS, OSI, DSI, EHP, AIGMS)
  File: app/services/profiling/profile.py
  Script: scripts/compute_profiles.py
  DB: organization_intelligence_profile (30 rows, all populated)
  - Industry mapping (logistics -> supply_chain_services) recorded
  - OSI scored conservatively when firmographics missing
  - Confidence penalized for thin data
  Tests: tests/test_profile.py (29 tests)

[BUILT] Normalization — weighted peer similarity
  File: app/services/normalization/engine.py
  Script: scripts/compute_normalization.py
  DB: benchmark_membership (30 rows, all have normalization_score)
  - Dimension weights: Industry 20%, RSS 20%, PGMS 15%, OSI 15%,
    DSI 15%, AIGMS 10%, Freshness 5%
  - Tier similarity: exact=1.0, adjacent=0.75, non-adjacent=0.5
  - Small-cohort relaxation (n=30 -> "adjacent" band, 0.85 factor)
  Tests: tests/test_normalization.py (20 tests)

[BUILT] Scoring — F-002 through F-014 + VCI
  Files: app/services/scoring/formulas.py (F-002,003,005,006,007)
         app/services/scoring/formulas_advanced.py (F-008 through F-014)
         app/services/scoring/vci.py
         app/services/scoring/engine.py (config loaders)
  DB: derived_data_item (554 rows)
  - F-002 Regulatory Exposure: reads JW from targets.yaml, RPW from
    regulator table, thresholds from formula_version
  - F-003 Benchmark Deviation: uses WEIGHTED peers (benchmark_weight)
  - F-005 Disclosure Maturity: reads element_checklist.csv
  - F-006 Transparency: completeness x clarity x specificity x explainability
  - F-007 AI Transparency: reads AI elements from checklist
  - F-008 Compound Risk: sum(risk x CM x RPW)
  - F-009 Confidence-Weighted: score x VCI
  - F-010 Overall Intelligence: reads weights from formula_version DB
  - F-011 Benchmark Percentile: weighted, honest cohort size
  - F-012 Trend Delta: built but no prior data (needs monitoring)
  - F-013 Alert Escalation: built but needs monitoring history
  - F-014 Report Confidence Index: validated/total x SR x NC
  - VCI: NLP 30% + Benchmark 25% + Regulatory 15% + Enforcement 15%
    + Source 15%. Labels + suppression at <40.
  Tests: tests/test_f002_f007.py (21), test_f008_f014.py (23),
         test_vci.py (8)

[MISSING] F-001 Source Reliability Score
  The formula_version row exists (F-001_v1 with weights), and the
  source_record table already has source_reliability_score pre-computed
  for 303 rows. But there is no app/services/scoring function that
  RECOMPUTES F-001. The existing scores were loaded with the corpus.
  GAP SEVERITY: Low — scores exist, just no recompute function.

[MISSING] F-004 Enforcement Correlation Score
  The formula_version row exists (F-004_v1) but NO implementation in
  app/services/scoring/. The PDF mentions "Enforcement Correlation
  (how closely the notice resembles things regulators have actually
  punished)" — this would use embedding similarity between clauses
  and enforcement_record.embedding. The embeddings exist (both tables
  have 384-dim vectors, ivfflat indexes built) but the scoring
  function to compute cosine similarity and produce a correlation
  score is NOT built.
  GAP SEVERITY: Medium — the data infrastructure (embeddings, indexes)
  is ready, the scoring function just needs to be written.

[BUILT] Findings — deterministic from fixed catalog
  File: app/services/scoring/findings.py
  DB: risk_finding (140 rows), finding_clause (356 rows),
      finding_enforcement (352 rows)
  - 8 finding types (AI-004, TRK-007, SH-002, RT-003, CR-001,
    DC-005, SEC-002, XB-001)
  - Deterministic: same inputs -> same findings (tested)
  - Each finding linked to triggering clauses + enforcement records
  Tests: tests/test_findings_reproducible.py (13 tests)

[PARTIAL] Regulator Heatmap
  The data exists (9 regulators with priority_weights JSONB covering
  all 8 domains), and the F-002 lineage includes per-regulator
  contributions. But there is NO dedicated heatmap computation
  function that produces a regulators x domains grid. The report
  assembly (Section 5) has a placeholder for the heatmap data but
  passes an empty list.
  GAP SEVERITY: Low-Medium — data is there, needs a small function
  to shape it into a grid.

[PARTIAL] clause_obligation matching
  Table exists (clause_obligation) with columns: clause_id,
  obligation_id, match_method, similarity. BUT: 0 rows populated.
  No script or function computes clause-to-obligation matches.
  The PDF mentions obligation matching as part of the intelligence
  layer. With embeddings on clauses and 154 obligations, this could
  use vector similarity, but it's not built.
  GAP SEVERITY: Medium — table ready, matching logic not implemented.

SUMMARY: WHAT'S MISSING OR INCOMPLETE

CRITICAL (blocks demo or core functionality):
1. [FRONTEND] Login -> dashboard redirect race condition. User can
   sign in but gets stuck on login page. Needs React auth flow fix.

MEDIUM (functionality gaps vs PDF spec):
2. [F-004] Enforcement Correlation Score not implemented. Formula
   version exists, embeddings exist, but no scoring function.
   Data infrastructure ready — needs ~50 lines of code.

3. [CLASSIFICATION] Live intake uses keyword classifier, not LLM.
   llm.classify() exists but isn't wired into POST /assessments.
   The 65% "other" corpus gap won't be resolved without this.

   matching function exists to link clauses to obligations via
   embedding similarity or keywords.

5. [REGULATOR HEATMAP] Data exists (9 regulators x 8 domains x
   priority weights) but no function shapes it into the grid that
   Section 5 of the report needs.

LOW (nice-to-have, not blocking):
6. [F-001] No recompute function (pre-computed scores exist).
7. [EXEMPLARS] All 43 are sme_cleaned=false. Section 8 of the
   report always shows placeholder. Needs SME review.
8. [STUB DATA] finding_type and recommendation_library have stub
   rows (sme_authored=false). Real SME content not loaded yet.
9. [PLAYWRIGHT] PDF renderer code exists but Playwright not
   installed. weasyprint works as fallback.
10. [F-012/F-013] Trend Delta and Alert Escalation built but
    return 0 (need monitoring history that doesn't exist yet).

COSMETIC / POLISH:
11. [FRONTEND] Pages functional but basic. Admin console shows
    data when CORS is correct. No report viewing page in frontend
    (report components exist but no route wires them to API).
12. [CORS] Backend CORS must include both localhost and 127.0.0.1.
    Currently requires manual .env config.

BOTTOM LINE
======================================================================

The PDF describes 5 stages with ~25 components. Of those:
  - 20 are FULLY BUILT and tested
  -  4 are PARTIAL (classification wiring, F-004, clause-obligation,
     regulator heatmap)
  -  1 has a FRONTEND BUG (login redirect)

The core intelligence pipeline (profile -> normalize -> score ->
findings -> narrative -> guardrail -> report) works end-to-end.
The two LLM jobs exist but aren't fully wired into the live path.
The scoring engine, VCI, reproducibility, and trust layer are solid.

To reach full PDF spec compliance, the top priorities are:
  1. Fix frontend login redirect
  2. Wire llm.classify() into POST /assessments
  3. Implement F-004 (enforcement correlation via embeddings)
  4. Populate clause_obligation matches
  5. Build regulator heatmap grid function
